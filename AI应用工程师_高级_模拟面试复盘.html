企业知识库问答系统：分块与检索策略设计
RAG
7.0
题目原文

你负责为公司内部构建一个企业知识库问答系统，知识源包括数千份 PDF、Confluence 页面和数据库文档，用户反馈的核心痛点是「答非所问」和「答案过期」。

  1. 如何设计整个 RAG 链路的分块与检索策略？说明分块方案的选择及理由。
  2. 针对「答案过期」，有什么机制保证检索到的是最新、最可信的内容？
你的回答（要点还原）
原始作答为语音转写，以下为忠实还原的要点整理，保留了你的原话逻辑与术语。
  • 分块：以结构化分块为主（企业内部最常用、有保障、适用面广）；另有按组、按行、递归切分等多种策略。
  • 落地做法：PDF 解析后转成 HTML 标签，标签本身有层级结构，按标签切分；切分采用递归切分，自顶向下，设定最大字符数，尽量保证一个标签的完整性落在同一窗口内；若父标签+子标签超出上限，则父标签放一个窗口、子标签放下一个窗口。
  • 检索链路：原则是「能上的优化都上」——查询重写 → 元数据/标签过滤 → 向量化检索 → 关键词检索与向量检索并行 → RRF 融合 → 取 Top-K → Rerank 精排 → 送入生成。
  • 进阶方向：企业知识可构建知识图谱增加图谱检索；当前主流是 Agentic RAG，由 Agent 循环做意图澄清、追问、答案汇总。
  • 答案过期（首次）：说明检索到了旧内容。① 分块时在 chunk 元数据中写入时间；② 在提示词中让模型关注时间问题。只想到这两点。
  • 答案过期（经提示后补充）：③ 新文档替换时直接删除旧文档，索引随之删除，就不会检索到；④ 多版本共存时，chunk 元数据中存版本与时间信息，检索时据此过滤。
面试官评价
✅ 做对之处
  • 分块有真实工程细节：HTML 结构化解析 + 递归切分 + 父子标签的窗口完整性处理，本质是 small-to-big / 父子 chunk 思路，说明确实落地过而非背概念。
  • 检索链路完整且符合主流：重写 → 过滤 → 混合检索 → RRF → Rerank，还主动提及知识图谱与 Agentic RAG 的演进方向。
  • 补充部分有救回：文档替换时删除旧索引、多版本用元数据过滤，方向正确。
⚠️ 待改进
  • 「能用的优化都上」是危险信号。每加一层（重写、RRF、Rerank、图谱）都有延迟与成本代价。高级别要讲清何时上、上哪一层、如何用评估集证明收益，而不是堆料。
  • 新鲜度首次回答偏弱，只落在「元数据打时间戳 + 提示词提醒」，而提示词约束是最不可靠的一层。
  • 缺增量同步管道：企业文档持续变更，靠手动传新删旧不现实，需要 webhook / CDC 驱动的自动 re-index 与失效 chunk 清理。
  • 缺 chunk 级有效期：除时间戳外应有 valid_from / valid_to，检索时直接过滤过期 chunk，而不是靠模型自觉。
  • 缺权威来源分级：同一主题多版本时，只按时间排序可能选错版本；应按来源权威度（官方制度库 > 部门主页 > 邮件归档）设权重或默认过滤。
  • 缺答案侧兜底：强制引用溯源（citation）、检测到来源时间冲突时提示「该信息可能过期」。
💡 标准答案要点

1. 分块策略（按文档类型分治，不搞一刀切）

  • 结构化文档（PDF/HTML/Confluence）：按标题层级与语义单元切分，保留 breadcrumb（章节路径）作为元数据，避免「断章取义」；表格单独处理（转 Markdown 或结构化摘要），代码块整体保留。
  • 粒度选择：主 chunk 300–600 token，overlap 10–15%；采用父子分块（small-to-big）——用小块做检索命中，命中后回溯父块送生成，兼顾检索精度与上下文完整性。
  • 元数据必带：文档 ID、标题、章节路径、来源类型、更新时间、版本、权限标签、权威等级。
  • 切分质量控制：抽检 50–100 条，检查是否有切断的表格、孤立代词、缺失标题；用「切分后单独看这块能否自洽回答」作为验收标准。

2. 检索策略（分层，按需启用，每层要有数据支撑）

  • 基础层：混合检索（BM25 + 向量），RRF 融合 —— 这是默认必选，收益最稳。
  • 优化层：查询重写 / HyDE / 多查询扩展；元数据预过滤（权限、时间、来源）。
  • 精排层：Cross-encoder Rerank 取 Top-5～8 —— 延迟 +50～200ms，需评估 ROI。
  • 增强层：知识图谱多跳检索、Agentic RAG（意图澄清/追问）—— 仅在多跳、指代消解类问题占比高时启用。
  • 每层都要挂在评估集上验证：加一层涨了几个点、多花多少毫秒，说不出来就不该加。

3. 内容新鲜度（三层机制，缺一不可）

  • 数据层：文档源 webhook / 定时增量扫描 → 变更检测（hash/版本号）→ 差量重建索引 → 删除或标记失效 chunk；建立「文档 → chunk」映射表，保证可精确删除。
  • 检索层：chunk 带 valid_from / valid_to / version / authority_score，查询时按时间窗与权威度过滤、加权；同主题多版本按「权威度优先、时间次之」排序。
  • 生成层：强制 citation（答案句 → chunk ID）；输出附「依据文档 + 更新时间」；来源过旧时显式提示「该信息更新于 X，可能已过期」；检测到多来源冲突时并列呈现而非强行合并。
加分项：把「过期」当成可观测指标——统计「引用 chunk 超过 180 天的回答占比」，作为数据治理的北极星之一。
📊 评分：7.0 / 10

分块与检索链路达到 7.5–8 分水平；新鲜度首次回答 5 分、补充后约 6 分。综合 7.0——合格的高级工程师答案，但在「按约束做架构取舍」与「数据生命周期管理」上还够不到 8+。

三个需求的技术选型：Prompt / RAG / 微调如何决策
技术选型
6.0
题目原文

业务方提出三个需求：

  • A：客服机器人，基于公司产品文档回答，文档每月更新，要求答案可溯源；
  • B：合同关键信息抽取（金额、签约方、日期等固定字段），已有 5000 条标注数据，要求输出格式严格稳定、延迟低；
  • C：把内部代码库的注释风格统一改写为公司规范风格。

三者分别选 Prompt 工程 / RAG / 微调 中的哪种（可组合）？请先给出决策框架（看哪几个维度），再套用到 A/B/C。

你的回答（要点还原）
  • A：典型 RAG 场景，模型知识无法更新，RAG 必选；提示词是各环节的基础设施，无论普通问答还是 RAG 各环节都需要好提示词；微调不需要，因为文档更新快、不涉及对模型本身知识的改动。
  • B：合同关键信息抽取是信息抽取 / 序列标注任务，肯定需要微调；RAG 不需要；提示词涉及但不是主要手段。
  • C：注释风格改写是 AI 写代码，用提示词即可，不需要微调，也不需要 RAG，因为不涉及召唤新知识。
注意：题目明确要求「先给决策框架」，你的回答直接进入三个结论，未立框架。
面试官评价
✅ 做对之处
  • A 判断准确：RAG 必选，理由（模型知识静态 vs 文档月更）说到本质；同时正确识别提示词是基础设施而非替代方案。
  • A 排除微调的理由成立：知识高频更新与微调的静态性冲突，抓住核心矛盾。
  • C 判断合理：纯风格改写不需要外部知识，Prompt + few-shot 足够，避免了过度工程。
  • 有基本的成本/工程直觉：不是所有场景都该上微调。
⚠️ 待改进
  • 没有给出决策框架——本题关键失分点。高级别应先立维度（知识时效性 / 输出空间是否封闭 / 标注数据量与质量 / 延迟与成本约束 / 可解释与可溯源要求 / 迭代频率），再逐项推导结论。
  • B 的判断停留在前 LLM 时代：「抽取 = 序列标注 = 必须微调」是 BERT 时代的路径。LLM 视角下的首选是 Prompt + 结构化输出约束（JSON Schema / function calling / constrained decoding）+ 校验重试。
  • 误读了 5000 条标注数据的信号：它证明的是「你有条件做微调以压缩成本与延迟」，而不是「必须微调」。
  • 忽略了 B 的「严格格式 + 低延迟」这两个约束，而它们恰恰是选型的决定性因素。
  • A 漏了「可溯源」的技术落点：citation、chunk 元数据回传、答案与来源绑定校验——需求里明写了却未落地方案。
  • C 缺工程视角：代码库级批量改写涉及并发调度、diff 校验、CI 集成、人工抽检，不是「提示词足矣」就结束。

应用到 A / B / C

需求判定方案组合
A 知识外部 + 月更 + 需溯源 → 不微调，RAG 为核心 混合检索 + Rerank + 查询重写；生成强制 citation（答案句绑 chunk ID）；prompt 版本化；评估集覆盖「知识库无答案 → 应拒答」

客服工具调用 Agent：控制循环、资金风险防护、成本优化
Agent 工程
6.5
题目原文

给客服系统加一个工具调用 Agent，完成「查订单 → 判断退款政策 → 发起退款 → 回复用户」的多步任务。工具：query_order、get_refund_policy、create_refund、send_message。

  1. 如何设计 Agent 控制循环（规划、工具选择、结果回灌、终止条件）？如何约束它不跑偏？
  2. create_refund 是写操作、有资金风险，加哪些防护？
  3. 上线后平均 6–8 轮工具调用，延迟高、成本高，如何优化？
你的回答（要点还原）
  • 控制循环：场景不复杂、步骤明确，用 ReAct 即可，不需要 Plan-and-Execute。假定已由前置意图识别路由到退款 Agent。
  • 关键判断：query_order 和 get_refund_policy 其实没必要让 Agent 自己决定调不调——任何用户进来都要查订单、判条件，应该由代码直接调用取数，Agent 只需根据结果回复。
  • 回复/追问环节要对 send_message 加约束，避免发散；判定为否决则直接结束，判定要退款则加置信度判断，达标才允许调 create_refund；工具内部再做最小权限与信息核查。
  • 写操作防护：不允许 Agent 独立完成，即使置信度高也要走审查流；置信度低的走人工；超金额订单强制人工审核；AI 可做二次审查。
  • 成本优化：调用多说明模型能力有问题或乱调工具，可针对当前工具和场景做垂直微调；长期看垂直场景微调后效果可能优于大模型，采用「微调 + 大模型兜底」。
面试官评价
✅ 做对之处
  • 第一问最有价值的判断：识别出查订单/查政策是确定性步骤，应由代码预取而非交给模型决策——这是「workflow 而非 agent」的正确直觉，很多候选人想不到。
  • ReAct vs Plan-and-Execute 取舍站得住：步骤明确、路径短，不需要重型规划器。
  • 写操作防护有层次：置信度门控 → 最小权限 → 金额阈值 → 人工复核 → AI 二次审查，方向都对。
  • 意识到 send_message 是对话出口，需要约束其发散。
⚠️ 待改进
  • 第一问缺关键控制点：未提终止条件（max_steps、超时、循环检测）、工具结果回灌裁剪（大 JSON 直接塞回上下文会爆 token）、失败重试与降级（工具报错时给模型什么反馈）。「约束它不跑偏」问的正是这些。
  • 写操作漏了最核心的几条：
    • 幂等性（idempotency key）——模型重试或循环会导致重复退款，资金场景第一大坑；
    • 两阶段提交 / dry-run：先「预演退款」返回「将退 ¥X 到 Y 账户」，用户确认后再执行；
    • 审计日志 + 可回滚：每笔写操作留 trace（触发者、模型决策依据、参数），支持冲正；
    • 速率与额度限制：同一用户/同一 Agent 单位时间退款次数上限，防 prompt injection 刷单；
    • 用户显式确认：涉及资金的最后一步应由用户点击，而非 Agent 自主执行。
  • 第三问是最大失分点，有两个问题：
    • 跳过诊断直接开药。正确第一反应是拆 trace：6–8 轮里哪几轮必要、哪几轮重复、哪几轮是解析失败重试、每步 token 多少。没有度量就优化。
    • 归因错误：「调用多说明模型能力有问题」——多数情况是工具设计/循环设计的问题。而且你第一问自己已给出最优解（订单与政策由代码预取，直接砍 2 轮），前后自相矛盾，面试官一定会抓。
    • 漏掉整排低成本高收益手段：并行调用、静态政策缓存、精简工具返回字段、Prompt/KV 缓存、结构化输出避免解析重试、简单意图走小模型、把自由循环改成状态机。
    • 微调放在第一顺位不合理：它最贵、最慢、最难维护，应在其他手段榨干后仍有收益才做。「微调 + 大模型兜底」方向没错，但顺序错了。
💡 标准答案要点

1. 控制循环设计

  • 先做形态判断：路径确定 → 用状态机/工作流（确定性最强、延迟最低、可测试）；路径不确定 → 才用 ReAct。本例其实 90% 可固化成状态机。
  • 工具设计：描述写清「何时用/不何时用/参数含义」；参数用 schema 强约束；工具粒度适中（过细导致轮次膨胀，过粗导致失控）；返回值做裁剪——只回必要字段 + 摘要，大结果落存储、上下文里放引用。
  • 结果回灌：结构化回灌（成功/失败/关键字段），错误码归一化，让模型能区分「可重试」「需换策略」「需转人工」。
  • 终止条件：max_steps（如 6）、单步超时 + 总超时预算、循环检测（相同工具+相同参数重复调用即中断）、置信度低于阈值 → 转人工。
  • 防跑偏：系统提示固化角色与禁止项；每步做参数校验；关键节点插入规则校验器（guardrail）；敏感工具白名单化。

2. 写操作防护（资金场景六件套）

① 幂等键    idempotency_key = hash(order_id + refund_intent_id)
             重复调用返回同一结果，不产生第二笔退款

⑤ 审计留痕  每笔写操作记录 trace_id、决策依据、参数快照，支持冲正
⑥ 人工兜底  金额 > 阈值、地址异常、历史风控标记 → 强制人工

  • 单点风险未提：网关是高可用关键路径，需多副本、无状态化、配置热更新、故障时的逃生通道（允许业务直连兜底）。

3. 成本与配额治理

② LLM-as-a-Judge 答偏了，是明显扣分项

  • 你描述的是 self-consistency / logprob 置信度，不是 LLM-as-a-Judge。
  • Judge 的本质是：用强模型按 rubric 给输出打分或做 pairwise 比较。可靠性问题不在 logits，而在下列偏差：
偏差表现缓解手段
位置偏差A/B 顺序影响结果交换顺序各评一次，取一致结果
冗长偏差更长答案得分更高rubric 明确「简洁性」，控制长度
自我偏好偏爱同家族模型输出用第三方模型当 judge，或多 judge 投票
评分漂移同答案不同批次分数不稳固定 judge 版本 + 温度 0 + 定期重标定
正确姿势：优先 pairwise 而非打分（人更易判断「哪个更好」）；judge 结果必须用 100–200 条人工标注做校准，算与人类一致性（Cohen's kappa / 一致率），不达标的 judge 不能当上线门禁。

③ 在线评估漏了无标注场景的核心指标

  • 应找隐式信号 + 业务结果指标：转人工率/升级率（最直接的质量代理）、会话解决率（containment）、平均轮次、追问率（反复追问=没答对）、答案复制率/引用点击率、会话中断率、重复提问率。
  • 点踩率须注意反馈稀疏且有偏（通常 <2% 用户会点），要用曝光做分母，且「无反馈」≠「满意」。
  • 上线必须做 A/B 或 interleaving 实验，不能只看绝对值趋势。

④ 回归防护缺「卡点」

  • CI 里设阈值门禁（关键指标下降 > 2% 阻断合并）、评估集版本与代码版本绑定、变更前后同分布对比、shadow 双跑（新链路跑影子流量但不返回用户）。
  • 灰度只说了「引一部分流量」，缺观测窗口、放量节奏、自动回滚条件。

3. LLM-as-a-Judge 的正确用法

  • 场景：开放式生成无法用精确匹配时（摘要、改写、多轮一致性）。
  • 设计：rubric 拆成 3–5 个可判定维度，每维度给 1/3/5 分的明确描述；输入包含问题 + context + 答案 + gold。
  • 可靠性：pairwise 优先；双向评分消除位置偏差；judge 用比被测模型更强的模型；温度 0；固定版本；定期用人工标注集算一致性（目标 kappa > 0.7）；多个 judge 投票取多数。
  • 失败模式防呆：答案长度做归一化处理；显式要求「先给证据再给分」，减少拍脑袋打分。

4. 在线评估

  • 北极星：会话解决率（未转人工且用户未重复提问的比例）。
  • 过程指标：转人工率、平均轮次、追问率、答案采纳率、引用点击率、会话中断率、P95 延迟。
  • 反馈指标：点赞/点踩率（以曝光为分母）、点踩原因分布（答非所问/信息过期/不完整/语气）。
  • 实验：A/B 分流 + 固定分流键；样本量按 MDE 计算，避免「3 天看结果」。

5. 回归防护管线

变更提交 → 静态检查 → 离线评估集全量跑（检索+生成+拒答）
        → 与 baseline 对比（分桶看，不只看总分）
        → 阈值门禁：核心指标↓>2% 或 拒答准确率↓  → 阻断
        → shadow 双跑 1–2 天（真实流量，不返回用户）
        → 灰度 5% → 20% → 50% → 100%，每档看在线指标 + 人工抽检
        → 异常自动回滚（prompt/索引/模型三者独立可切）
📊 评分：6.0 / 10

Q1 评估集建设 6.5；Q2 LLM-as-Judge 3.5（概念性错误，且是高级岗位高频考点）；Q3 在线指标 5.5（有常识，缺无标注场景方法论）；Q4 回归防护 7.0（最扎实）。综合 6.0。

提醒：评估能力是 AI 应用工程师从「能搭 demo」到「能对结果负责」的分水岭。这题答不好，面试官会怀疑你做过的东西是否真的被量化验证过。

6
行为面试：一个主导推动但中途失败的项目
行为 · STAR
6.5
题目原文

讲一个你主导推动、但中途遇到重大阻力或失败的 AI 项目，用 STAR 说清：情境与角色、任务与难点、关键决策与阻力处理、量化结果与「如果重来会改什么」。重点讲你的决策和你犯的错，不要只讲成果。

你的回答（要点还原）
  • 项目：类 Coze 的工作流平台，做了一个「输入自然语言需求 → 一键生成可运行工作流」的功能，目标是降低搭建门槛。你是主要开发。同期还规划了 MCP 与智能体市场。
  • 结果：功能草草收尾，用户使用不多。
  • 核心问题：生成的工作流不能直接执行，需人工微调（配参数、补输入）；部分场景生成结果有错。
  • 根因：工作流是 DAG，但节点通过属性（端口）相连，每个组件上下游可连什么被严格限定；AI 必须同时掌握这些约束才能生成合法图，约束多且存在「临时为特定用户做的属性」；此外变量传递靠节点连线，没有 Coze 那样的变量空间机制，因此不支持嵌套，表达力受限。
  • 当时的应对：把上下游约束、组件描述、属性描述全塞进系统提示词；为让组件能跑，给大量默认值（如文件解析组件给固定默认路径）。优化多轮后，简单场景效果尚可、可直接运行，复杂场景仍不行；提示词过长导致生成时间很长。
  • 如果重来：① harness（工程脚手架/约束保障）要做足；② 架构要轻便通用，不要堆死限制（但既有业务限制导致难改）；③ 当时 ReAct 范式未普及，现在可用 ReAct 替代一次性生成；④ 提示词拆分——把「查上下游依赖」做成工具、组件信息按分组惰性加载，避免提示词塞满、耗 token、噪声稀释注意力；⑤ 最主要仍是架构问题。
面试官评价
✅ 做对之处
  • 讲失败讲得真诚且具体，没包装成成功故事——高级面试里这是加分项，面试官更怕听到「全都顺利」。
  • 根因分析有真正的技术深度：把失败归因到数据模型的表达力（端口连线的强类型 DAG vs 变量空间 + 嵌套），而不是「模型不够强」。这个判断是对的，且很少有人能说到这一层。
  • 技术细节可信：约束进 prompt、给默认值让工作流「可跑」、prompt 过长导致延迟、注意力稀释——都是真实踩过的坑。
  • 反思可操作：给出具体替代方案——组件规格查询做成工具、按分组惰性加载、用 ReAct 替代一次性生成。这是本题最有价值的部分。
⚠️ 待改进
  • 完全没有数字。全程「用的不是很多」「好了一点」「草草了事」。必答：生成成功率从多少到多少？简单场景占比？用户留存/使用率？生成耗时？没有量化，面试官无法判断影响规模，也会怀疑你们当时是否真度量过。
  • STAR 结构松散：大量架构细节，但「你做了哪些决策、和谁有分歧、你怎么推动」几乎空白。全程「我们」，个人贡献边界不清。
  • 缺「止损与向上管理」：项目做不下去时，你有没有推动——收敛场景（只支持 Top 10 高频模板）？改成「生成草稿 + 人工确认」的半自动形态？争取重构窗口？主动建议砍掉？你只说了「架构不好改，有既有业务限制」，这是解释不是行动。
  • 有一个更狠的反思没做：用户「需要微调才能用」本身可能是需求判断错误。也许用户根本不需要「一键生成可跑的完整工作流」，而需要「从相似模板改一改」。你们一开始有没有验证这个假设？有没有拿「模板市场 + 复制修改」做 baseline？没做 baseline 就投入做生成，是比架构更根本的失误。
  • 「当时 ReAct 还没流行」略带外部归因：作为背景可以，但同期用语法引导生成（grammar-constrained decoding）也能大幅提升 DSL 生成合法率，这个方案你没提。
💡 标准答案要点（同一件事怎么讲才 8 分）

S：平台 3 万用户中约 40% 卡在搭建门槛，我们做 NL→工作流生成，我负责生成链路，目标「生成即跑通率 ≥ 70%」。

T：核心难点是 DSL 的强约束（端口类型、上下游兼容），模型必须生成结构合法的图。

A：① 先做 baseline——用「模板检索 + 槽位填充」跑了一遍，跑通率 55%，证明纯生成收益有限；② 生成侧引入 schema 约束解码，把非法边降到 X%；③ 把组件规格从 prompt 挪到工具调用，prompt 从 12k 降到 3k，P95 从 18s 降到 7s；④ 推动把「一键可跑」改成「生成草稿 + 一步确认」，采纳率升到 X%。

R：复杂场景跑通率仍只有 30%，我判断根因在 DSL 表达力（无变量空间、不支持嵌套），提出重构方案但未获资源，项目转入维护。复盘：我应该在第二个月就用 baseline 数据说服团队收敛场景，而不是先做通用方案。

STAR 得分要点（面试官在看什么）

要素必须出现的信号
